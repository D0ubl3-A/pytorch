# Operator Benchmark Triage & Regression Validation Setup

This document summarizes the complete setup for automated operator benchmark triaging and regression validation in PyTorch.

## Overview

Two integrated systems have been created:

1. **Benchmark Triage Flow**: Analyzes PRs to determine which benchmarks should run
2. **Regression Validation Flow**: Analyzes benchmark results to detect performance regressions

Both follow the same two-stage pattern used by `claude-issue-triage` and the `treehugger` skill in pytorch-gha-infra.

## Architecture

### Pattern: Two-Stage Workflow

Both flows use a two-stage workflow pattern for security:

```
Stage 1: Capture Event Data (minimal permissions, OSS-accessible)
    ↓ (artifact)
Stage 2: Analyze + Apply (protected environment)
    ├─ Job 1: Claude Analysis (READ-ONLY)
    │   └─ Produces structured JSON output
    └─ Job 2: Apply Actions (WRITE permissions)
        └─ Posts comments, adds labels
```

## Flow 1: Benchmark Triage

### Trigger

```yaml
on:
  pull_request:
    types: [opened, synchronize, reopened]
    paths:
      - 'aten/src/ATen/**'
      - 'torch/**'
      - 'c10/**'
      - 'benchmarks/operator_benchmark/**'
  workflow_dispatch:  # Manual trigger
```

### Process

1. **Stage 1** (`claude-operator-benchmark-triage.yml`):
   - Captures PR number
   - Uploads as artifact

2. **Stage 2** (`claude-operator-benchmark-triage-run.yml`):
   - **Job 1: analyze** (READ-ONLY, runs in `bedrock` environment)
     - Uses GitHub MCP server
     - Fetches PR files and diffs
     - Analyzes changed files using `SKILL.md`
     - Maps to benchmarks using `benchmark_mapping.json`
     - Produces `/tmp/benchmark_analysis_output.json`
   
   - **Job 2: apply-benchmarks** (WRITE permissions)
     - Parses JSON output
     - Posts summary comment to PR
     - Adds labels (`perf-critical`, `perf-impact`)
     - TODO: Trigger actual benchmark runs

### Output Format

```json
{
  "pr_number": 12345,
  "regression_risk": "high|medium|low|minimal",
  "benchmark_scope": "targeted|short|long|full|none",
  "targeted_benchmarks": ["matmul", "conv"],
  "devices": ["cpu", "cuda"],
  "priority_level": "critical|high|medium|low",
  "rationale": "Explanation of why these benchmarks were selected",
  "estimated_completion_time": "5-10 minutes per device"
}
```

### Example PR Comment

```markdown
## 🔬 Operator Benchmark Analysis

**Benchmark Scope:** `targeted`
**Regression Risk:** `high`
**Priority:** `critical`
**Devices:** cpu, cuda
**Estimated Completion Time:** 5-10 minutes per device

**Rationale:**
PR modifies core matmul kernel implementation in aten/src/ATen/native/LinearAlgebra.cpp,
affecting all matrix multiplication operators.

**Targeted Benchmarks:** matmul, mm, bmm, addmm

---
🤖 *This analysis was generated by Claude Code.*
```

## Flow 2: Regression Validation

### Trigger

```yaml
on:
  workflow_run:
    workflows: ["operator_benchmark", "operator_microbenchmark"]
    types: [completed]
  workflow_dispatch:  # Manual trigger
```

### Process

1. **Job 1: analyze-regression** (READ-ONLY, runs in `bedrock` environment)
   - Extracts PR number from benchmark workflow
   - Downloads benchmark result artifacts
   - Loads baseline data from CSV files (`*_expected_*.csv`)
   - Compares current vs baseline performance
   - Applies regression thresholds
   - Produces `/tmp/regression_analysis_output.json`

2. **Job 2: post-results** (WRITE permissions)
   - Parses regression analysis
   - Formats as markdown table
   - Posts comment to PR
   - Adds labels (`perf-regression`, `do-not-merge`)

### Regression Thresholds

| Change | Severity | Action |
|--------|----------|--------|
| >20% slower | **Critical** | Block merge |
| 10-20% slower | **High** | Require investigation |
| 5-10% slower | **Medium** | Approve with note |
| 2-5% slower | **Low** | Minor note |
| <2% | - | Noise (ignore) |
| Faster | **Improvement** | 🎉 |

### Output Format

```json
{
  "pr_number": 12345,
  "overall_result": "regression_detected|no_regression|improvement|inconclusive",
  "summary": {
    "total_operators_tested": 50,
    "regressions_detected": 2,
    "high_regressions": 1,
    "medium_regressions": 1
  },
  "regressions": [
    {
      "operator": "torch.matmul",
      "severity": "high",
      "baseline_time_us": 150.2,
      "current_time_us": 175.8,
      "percent_change": 17.0
    }
  ],
  "recommendation": "block_merge|require_investigation|approve_with_note|approve"
}
```

### Example PR Comment

```markdown
## ⚠️ Performance Regression Detected

**Benchmark Run:** [View Results](https://github.com/pytorch/pytorch/actions/runs/...)

### Regressions Found

| Operator | Config | Severity | Change | Baseline | Current |
|----------|--------|----------|--------|----------|---------|
| torch.matmul | M=1024, N=1024, K=1024 (CUDA) | HIGH | +17.0% | 150.2μs | 175.8μs |

### Analysis

The regression in torch.matmul is concerning as it's a core operator with high usage.
Changes to aten/src/ATen/native/cuda/Blas.cpp may have affected performance.

### Recommendation

🛑 **Block merge until investigated**

Please review the performance impact and either:
1. Fix the regression
2. Provide justification for the performance trade-off
3. Add a TODO to address this in a follow-up

---
🤖 *Automated analysis by Claude Code*
```

## Benchmark Mapping

The `benchmark_mapping.json` file maps code patterns to benchmark tests:

| Code Pattern | Benchmarks |
|--------------|------------|
| `*matmul*`, `*LinearAlgebra*` | `matmul_test.py`, `mm_test.py`, `bmm_test.py`, `addmm_test.py` |
| `*conv*.cpp` | `conv_test.py` |
| `*norm*.cpp` | `batchnorm_test.py`, `layernorm_test.py`, `groupnorm_test.py` |
| `*activation*` | `activation_test.py`, `gelu_test.py`, `softmax_test.py` |
| `torch/ao/quantization/*` | All `q*_test.py` benchmarks |
| Dispatcher/autograd | `all_short` (broad impact) |

**75 operator benchmarks** are tracked in total.

## Security Model

### Read-Only Claude Jobs

Both analysis jobs run with restricted permissions:
- **AWS**: Read-only IAM role via OIDC
- **GitHub**: Read-only tokens via GitHub MCP server
- **Write tool**: Restricted to specific output files via pre-hooks
- **Prompt injection protection**: Explicit security constraints

### Separate Write Jobs

Write operations (comments, labels) are handled by separate jobs:
- Run after Claude analysis completes
- Parse structured JSON output
- Apply validated actions only

### Two-Stage Pattern

Stage 1 (minimal permissions):
- Can be triggered by OSS contributors
- No access to secrets or protected environments

Stage 2 (protected environment):
- Runs in `bedrock` environment
- Has AWS and GitHub access
- Claude job is still read-only
- Separate job handles writes

## Comparison to Existing Patterns

### Similar to `claude-issue-triage`

✅ Two-stage workflow for OSS accessibility
✅ Structured JSON output
✅ Validation hooks
✅ Separate read/write jobs

### Similar to `treehugger` skill

✅ Investigation-focused skill
✅ Structured actions JSON
✅ Pre/post/stop hooks
✅ Read-only analysis + write job
✅ Security constraints

### Differences

- Triage analyzes PR diffs (not alerts/logs)
- Regression compares performance metrics (not logs)
- Output triggers benchmarks (not creates issues)
- Works with MCP GitHub server (not AWS/CloudWatch)
